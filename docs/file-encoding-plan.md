# talent-cli 文件编码处理（read / edit / write / grep）

## 一、原则（2026-11-20 定论）

- **只认 UTF-8，不猜其他编码。** 不提供任何编码配置，也不要求用户或模型指定文件编码。用户的文件可能是任何编码，软件给所有人用，编码只能从文件内容判断，且同一份文件在任何机器上结果一致（不看系统默认编码）。
- **不写坏文件。** 解不了的字节原样保留；不会把字符写成 `?` 或 `�`；不会让一个文件混入两种编码。
- **不引导重写。** 拒绝提示只说明原因和可行的做法（只改 ASCII、告诉用户），不出现“整份重写”“转成 UTF-8”“在配置中指定编码”。

## 二、编码判断（`TextEncodings.detect`，四个工具共用）

按顺序，命中即停：

1. **BOM**：UTF-8 / UTF-16LE / UTF-16BE。有 BOM 时编码是确定的（UTF-32 的 BOM 不认）。
2. **整份严格合法的 UTF-8**（含纯 ASCII）。
3. **大体是 UTF-8**：合法多字节字符数 ≥ 4 × 坏字节段数。仍按 UTF-8，坏字节原样保留（典型场景：UTF-8 文件里粘进一段别的编码）。
4. **不是 UTF-8**：其余情况。按 UTF-8 替换模式显示，坏字节原样保留，新写入的内容不能含非 ASCII 字符。

超过 10 MB 的文件只取开头 1 MB 判断（在最后一个换行处截断）。主编码 `fileCharset`（受保护字段，默认 UTF-8）不是 UTF-8 时，第 2 步改为“按它解码没有坏字节”，没有第 3 步。

read 首行的 `Encoding` 字段（固定英文）：`UTF-8`、`UTF-8 with BOM`、`UTF-16LE with BOM`、`UTF-8, 2 undecodable bytes shown as U+FFFD`、`not UTF-8, 120 undecodable bytes shown as U+FFFD`，超大文件追加 `, sampled first 1 MB`。

## 三、各工具行为

| 工具 | 行为 |
|---|---|
| read | 首行带 Encoding；编码按整份文件判断，翻页不变；带 UTF-16 BOM 的文件按 BOM 解码（以前因 NUL 字节被当成二进制拒绝）；坏字节显示为 `�` |
| edit | 按判断出的编码编辑，BOM 与解不了的字节原样写回；new_str 里编码表示不了的字符（孤立代理等）拒绝并指出字符与位置；“不是 UTF-8”的文件写入非 ASCII 拒绝；含坏字节的文件匹配失败时追加说明 |
| write | 新建文件用 UTF-8；覆盖已有文本文件时沿用它的 BOM（UTF-8 / UTF-16）；原文件有坏字节而内容含 `�` 时拒绝（覆盖会永久丢失原字节）；原文件“不是 UTF-8”而内容含非 ASCII 时拒绝；二进制文件不保护 |
| grep | 带 UTF-16 BOM 的文件按 BOM 解码（用中文能搜到）；其余按 UTF-8 替换模式解码，UTF-8 字节预筛不变；结果不附加编码说明 |

本地与虚拟来源同口径。系统提示有一条：文件按 UTF-8 处理（带 BOM 的按 BOM），read 首行的 Encoding 注明文件编码，edit / write 会按它保存，不要自己转换编码。

## 四、已知限制

- GBK、Big5、Shift_JIS 等非 UTF-8 文件：中文显示为 `�`、用中文搜不到、不能写入非 ASCII 字符；代码本身照常读、搜、改，文件不会被写坏。要彻底解决由用户自己把项目转成 UTF-8，工具不主动引导。
- 字很少且字节恰好是合法 UTF-8 的 GBK 文件（如只有一个“注”字）会当成 UTF-8；字节仍原样保留。

## 五、决策记录

- 第一版曾自动识别 GBK（候选编码 + 中文内容检查）并提供 `FileEncodingPolicy`（候选编码、按路径指定编码）。实测几个字的韩文、日文注释会被判成 `GBK detected` 并显示成错字；要支持日、韩、繁体还得再加多套检查和“参考邻近文件”的推断，阈值靠少量样本调出，误判仍会有；配置又违背“不让用户指定编码”的原则。opencode 与 claude-code-java 的做法也是只认 UTF-8（另处理 BOM）。因此改为只认 UTF-8，删除 GBK 识别、`FileEncodingPolicy`、HarnessEngine 上的配置接线、grep 的多编码预筛与结果末尾编码说明，以及为 GBK 做的大文件优化（只解码当前页、原字节跳行、复用识别结果）。
- 比 opencode 多做的两处保留：非 UTF-8 文件允许修改（坏字节原样保留，只拒绝写入非 ASCII），而不是整个拒绝；write 覆盖前检查，避免把原字节永久写成 `�`。
- UTF-16 BOM 保留：编码确定、无需猜测，PowerShell 重定向输出就是这种文件；判断只看开头两个字节，不影响性能。
