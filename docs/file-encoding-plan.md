# talent-cli 文件编码优化方案（read / edit / write / grep）

> 状态：2026-11-20 用户确认，按本方案实施。第七节四项均按建议拍板。

## 一、目标

1. **看得懂**：read 读 GBK 文件显示真实中文，首行告诉模型文件编码及可信程度。
2. **找得到**：用中文能搜到 GBK 文件里的内容，英文搜索结果不变。
3. **改不坏**：edit / write 按原编码保存；不能保证安全的写入一律拒绝，文件不动，报错说明原因和下一步。

### 不变式

| 编号 | 规则 |
|---|---|
| I1 | 合法 UTF-8 文件（含纯 ASCII），四个工具行为与改前逐字节相同，唯一差别是 read 首行多编码字段 |
| I2 | edit 只改被替换的那几处，其余字节原样保留，并用“重新编码后与原文件逐字节相同”校验 |
| I3 | 任何工具都不会把表示不了的字符写成 `?` 或 `�` |
| I4 | 每次拒绝都保持文件不动，报错含原因、后果、下一步 |
| I5 | 同一份文件内容，四个工具判断出的编码一致 |

## 二、编码检测（共用）

`TextEncodings.detect(bytes, 相对路径, FileEncodingPolicy)` → `DecodedText`（charset、bom、source、rawBytes、sampled、text、label()）。

判断顺序（命中即停）：

1. **BOM**：UTF-8 / UTF-16LE / UTF-16BE，放在二进制判断之前。UTF-32 不支持。
2. **路径规则**（用户配置，如 `**/*.properties` → ISO-8859-1）。解不通时降为 UNKNOWN。
3. **整份严格合法 UTF-8**（末尾不容许残缺）→ UTF-8。
4. **大体是 UTF-8、夹少量坏字节** → MIXED（按 UTF-8，坏字节原样保留）。
5. **候选编码**（默认 GBK；系统默认编码为 GBK 以外的多字节中日韩编码时加入候选）：解码无错误 + 往返逐字节相同 + 内容质量检查（双字节字符中 GB2312 一级汉字与中文标点占比、常用字覆盖率）。
6. 都不满足 → UNKNOWN（按 UTF-8 显示，坏字节原样保留）。

单字节编码不自动猜，只通过路径规则指定。10 MB 以内整份检测，超过则检测开头 1 MB 并标 `sampled`。

## 三、各工具行为

### read
首行追加 `Encoding: ...`（固定英文，不走 i18n），检测针对整份文件，翻页不变：

| 情况 | 字段 |
|---|---|
| 合法 UTF-8 | `UTF-8` |
| BOM | `UTF-8 with BOM` / `UTF-16LE with BOM` |
| 路径规则 | `ISO-8859-1 configured` |
| 自动识别 | `GBK detected` |
| 大体 UTF-8 | `UTF-8, 3 undecodable bytes shown as U+FFFD` |
| 识别不出 | `unknown, 12 undecodable bytes shown as U+FFFD` |
| 超大文件 | 追加 `, sampled first 1 MB` |

### edit
old_str 与按检测编码解码的文本匹配；new_str 按同一编码严格编码；原字节原样写回，往返校验兜底。

| 文件状态 | new_str | 结果 |
|---|---|---|
| UTF-8 / BOM / UTF-16 / 规则 / GBK | 可表示 | 按原编码保存，BOM 保留 |
| 同上 | 有不可表示字符 | 拒绝，指出字符与位置 |
| MIXED | 任意 | 按 UTF-8 保存，坏字节保留 |
| UNKNOWN | 纯 ASCII | 允许 |
| UNKNOWN | 含非 ASCII | 拒绝 |

非普通 UTF-8 时成功提示注明保存编码。

### write

| 原文件 | 写入内容 | 结果 |
|---|---|---|
| 不存在 | 任意 | 有路径规则按规则，否则 UTF-8 无 BOM |
| UTF-8 / UTF-8 BOM | 任意 | UTF-8，保留 BOM，不写重复 BOM |
| UTF-16 BOM | 任意 | 按原字节序带 BOM 写 |
| GBK / 规则 | 可表示 | 按原编码写 |
| GBK / 规则 | 有不可表示字符 | 拒绝 |
| MIXED / UNKNOWN | 含 `�` | 拒绝，提示改用 edit |
| MIXED | 不含 `�` | 按 UTF-8 写 |
| UNKNOWN | 纯 ASCII | 允许 |
| UNKNOWN | 含非 ASCII | 拒绝 |

### grep
文件整份合法 UTF-8 时走原快速路径；否则按检测编码解码。字节预筛为 UTF-8、各候选编码、规则编码各准备一份模式字节，任一命中才逐行匹配（UTF-16 BOM 文件与含 `�` 的模式不预筛）。命中非 UTF-8 文件时，结果末尾追加一行说明各文件的编码。

### 提示文案
按“原因、后果、下一步”三段写；任何提示都不出现“整份重写”“转成 UTF-8”的引导。

## 四、配置

- talent-cli：`FileEncodingPolicy`（候选编码、路径规则、新建文件编码），`TerminalTalent.setFileEncodingPolicy(...)`。
- harness：`HarnessOptions` 对应字段，`HarnessEngine` 构建 TerminalTalent 时传入。
- 不提供工具参数里的 encoding；不内置 `.properties` 规则。

## 五、里程碑

M0 提交前序改动 → M1 write 覆盖保护 → M2 检测函数与语料 → M3 read → M4 edit / write → M5 grep → M6 UTF-16 → M7 配置与收尾。

## 六、已知限制

- 字很少且恰好是合法 UTF-8 的 GBK 文件会被当成 UTF-8，只能靠路径规则指定。
- 编码误判时损失有上限：未改字节不变，最坏是新写入的非 ASCII 字符编码不对。
- 不在范围：edit 原子写（临时文件 + 改名）、显式编码转换。

## 七、实施结果（2026-11-20）

M1–M7 已全部完成，代码未提交。

- **实现**：`TextEncodings`（包内，识别与编解码）、`FileEncodingPolicy`（公开，候选编码与路径规则）；read / edit / write / grep 本地与虚拟来源全部接入；harness 增加 `fileEncodingPolicy` 配置。
- **与方案的差异**：
  1. 内容检查多了一项：汉字 ≥ 10 个时，首字节在 C9–D7 的汉字须 ≥ 10%。原因：EUC-KR 韩文按 GBK 解码后常用字覆盖率约 47%，与 50% 阈值太近；而韩文只落在 B0–C8 行，真实中文的高频字（是/中/一/在/这/有）都在 C9–D7 行。语料实测：中文代码/散文为 27%–38%，韩文为 0%。
  2. 编辑/写入成功的编码说明另起一行（“已按 GBK 编码保存。”），而不是括号接在原句后：英文资源值不能以空格开头。
  3. GB18030 四字节字符不计入 (a) 项的占比，否则配置了 GB18030 也识别不出含扩展汉字的文件。
- **验收**：cli 796 例 0 失败；harness-core 失败清单与改动前一致；grep 基准纯 UTF-8 仓库差异在噪声范围内（−7% 至 +8%）；14 处故障注入 13 处被发现（存活的 1 处只影响性能）。
- **仍未做**：Windows 上补跑等价性与 UTF-16 用例；soloncode 设置页的配置入口。

## 八、实施后的性能收紧（2026-11-20）

复盘时发现四处实现没按最省的方式做，已收紧，输出逐字不变（基准五类场景与收紧前逐字对照）：

1. **read 只解码当前页**：从内存字节流式解码；UTF-8 与识别出的 GB 系编码翻页时在原字节上跳行（0x0A / 0x0D 字节就是换行）；已知超过 10 MB 的直接抽样，不再先读 10 MB。
2. **识别结果复用**：候选编码保留严格解码结果给 edit / grep；无坏字节时快速整体解码；已验证往返的不再重验；往返检查分块比较；GB 内容检查放在解码前。
3. **grep 先按各编码字节预筛、再识别**：主编码与各候选编码各一份模式字节；路径规则单独判断；无规则时先整份严格按 UTF-8 解码，成功即用。
4. **保字节编码走字符数组**，无原字节映射字符时整体编码，仍严格。

实测（三轮中位数）：read 5 MB UTF-8 首页 14.8→8.6 ms，GBK 首页 49.5→42.2 ms，20 MB 文件 5.9→2.0 ms；edit 5 MB UTF-8 99→58 ms、GBK 156→94 ms；grep GBK 语料中文无命中 41.6→31.9 ms；纯 UTF-8 仓库的 grep / ls / glob 持平。剩余固定开销：大文件 read 首页要整份读入并扫描 UTF-8；GBK 文件要做一次完整候选检查（5 MB 约 27 ms）。测试见 `TerminalEncodingFastPathTest`，16 处故障注入全部被发现。
